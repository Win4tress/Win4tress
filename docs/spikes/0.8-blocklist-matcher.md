# Spike 0.8: blocklist compile and memory-mapped lookup

**Status:** Passed (2026-10-26), by a wide margin on every criterion. The SPEC §13 design (keyed 64-bit hashes in a sorted array, memory-mapped, the name and each parent looked up) is kept as is; no trie needed.
**Tool:** [tools/spikes/blocklist-bench](../../tools/spikes/blocklist-bench) on [`w4-dns`](../../crates/w4-dns) (the product's matcher, not throwaway code): `compile <out> <pad-to> <lists…>`, then `lookup <out> <queries>` in a fresh process, the way the resolver opens the file.
**Machine:** Windows 11 Enterprise VM (the dev PC), release build.

The lookups were a third subdomains of listed names (blocked through a parent) and two thirds unlisted names 3 to 6 labels deep, so most needed every parent checked. With 100 regex rules on top, p99 was 1.9–2.3 µs.

**Compiling** (when a list is downloaded, not at start): parsing ~70 ms per 200k-line list, compiling 1M domains 117 ms, 0.67 s from text to file in all.

## Findings

1. **No need for a trie.** Hashing each suffix and binary-searching 1M sorted hashes costs about a microsecond. A name with five labels is five hashes and five searches of ~20 steps.
2. **The memory is the file.** A mapped page counts once touched; with every page touched the working set didn't grow past the run's own numbers. 10 bytes a domain: 8 for the hash, 2 for the list it came from.
3. **A 64-bit keyed hash is enough.** With a fresh SipHash key per file, a false match needs a 64-bit collision among ~5 suffixes; at 1M entries that's around 1 in 4 × 10¹² lookups, and nobody can craft one without the key.
4. **Replace, don't rewrite, a mapped file.** Windows won't replace a file that's mapped. The resolver must load a new file under a new name and drop the old mapping before the old file is deleted.
