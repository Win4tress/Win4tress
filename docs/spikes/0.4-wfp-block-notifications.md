# Spike 0.4: WFP block notifications → Windows Firewall rule

**Status:** Passed (2026-10-25). Every block maps to the rule that caused it, including the default outbound block. The latency target is met by real-time ETW (`Microsoft-Windows-WFP` event 1001) in its own session: about 0.13 s from the connection attempt to our callback. The WFP net-event subscription has the same information but arrives in ~1 s batches.
**Tool:** [tools/spikes/fw-probe](../../tools/spikes/fw-probe), elevated: `blocks` (mapping, net events), `default-block` (default outbound block), `etw-latency` (ETW session settings)
**Machine:** Windows 11 Enterprise VM (the dev PC), `windows` 0.62.2, `ferrisetw` 1.2.0. Net-event collection already on (`FWPM_ENGINE_COLLECT_NET_EVENTS` = 1, keywords 0), auditing off.

Rules that blocked anything applied only to a private copy of `curl.exe`, which made HTTPS connection attempts by IP (no DNS involved). Every spike rule was removed at the end; none were left. No trace sessions were left either.

## Findings

1. **A notification carries what Ask to Connect needs.** Both sources give:
   - the app's NT path (`\device\harddiskvolume3\…\w4fwtest.exe`)
   - local and remote address and port
   - layer and the blocking filter's ID

   ETW event 1001 also has the user SID and profile. It has **no protocol field**: take it from the layer, or fill it from the net event that follows about a second later. The filter leads to the rule by name, and win4tress rule names end with the rule ID (SPEC §7.2).
2. **One rule becomes several WFP filters.** A single outbound rule produced 3 filters at the IPv4 connect layer alone. Mapping must go filter → name → rule, never assume one filter per rule. The default outbound block is three filters named "Default Outbound".
3. **Resolve the filter ID at once.** In the first default-block run, the filter IDs were looked up 2.5 s after the default was restored, and none existed any more: Windows Firewall rebuilds its WFP filters when the default changes. The second run snapshotted the filters while the block was in force, and the mapping worked. The service must look up each filter as the event arrives (with ETW that's ~0.1 s later), keep a small cache of recent IDs, and treat a missing ID as "rule changed since".
4. **Net events are batched by Windows (~1 s).** `FwpmNetEventSubscribe4` delivered the default-block drops after up to 1,004 ms. In the `blocks` run, three attempts ~430 ms apart arrived together (median 0.6 s, max 1.0 s). The subscriber can't speed this up.
5. **Real-time ETW is fast, but its delay is set by the session's buffering.** The event's own timestamp is accurate: about 10 ms after the attempt starts, which is when the drop happens. The delay is all in delivery:

   | Session settings (5 attempts each) | Event → callback |
   |---|---|
   | 250 ms flush, per-CPU buffers (the traffic collector's settings) | 514–526 ms |
   | 250 ms flush, one set of buffers (`EVENT_TRACE_NO_PER_PROCESSOR_BUFFERING`) | 255–263 ms |
   | 50 ms flush, per-CPU buffers | 113–130 ms |
   | 1 s flush, per-CPU buffers | 1,015–2,016 ms |

   With per-CPU buffers, a quiet provider's events arrive about **twice the flush timer** late; with one set of buffers, about one flush timer late. They don't arrive spread evenly between 0 and the flush timer, as one might expect.
6. **Use a separate session for drops.** Block events are few, so a small session with a short flush costs almost nothing. Keeping it apart from the high-volume traffic collector means lost traffic events under load can't take block events with them, and each session can be restarted on its own.
7. **The default-block window affects everything without an allow rule.** During the 1.7 s window, `claude.exe` (this session's client) had 2 connection attempts dropped. In the first run, Defender and Edge were dropped too. This is the cost Ask to Connect's baseline allow-list exists to cover (SPEC §7.4).
8. **Reading WFP filters needs the BFE engine handle (admin).** Fine for the service.
9. **No inbound drops occurred** in a 30 s idle window, so there's no sample of the inbound default block. With match-any keywords at 0, multicast and broadcast drops aren't collected (by design; we don't want them).

## Design consequences

- **Block events (SPEC §6, §7.4, §7.9):**
  - Primary source: a dedicated real-time ETW session on `Microsoft-Windows-WFP`, keyword `0x10`, event 1001, with a 50 ms flush.
  - Filter ID → rule is resolved immediately through WFP.
  - The `FwpmNetEventSubscribe` stream is kept as a cross-check and as the protocol source.
- **The traffic collector's delivery is about 0.5 s, not 0.25 s.** That's the 250 ms flush with per-CPU buffers. It explains much of the late-event allowance in Phase 1 (`CLOSE_LAG_MS`). Measured here on a quiet provider; a busy session fills and hands over buffers sooner.
