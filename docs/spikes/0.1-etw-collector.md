## Findings that change the design

1. **Use the process ID in the event data, never the header.** The header process ID was wrong on **82%** of data events (a 45 s run).
2. **Flush timer drives delay.** With ETW's default 1 s flush timer, events arrived about 1.5 s late, and the first event after restart took 2.0 s. Using `EVENT_TRACE_USE_MS_FLUSH_TIMER` with 250 ms cut restart-to-first-event to 0.5 s. `ferrisetw` doesn't define the flag; the probe sets the raw bit.
3. **Bucket traffic by event timestamp, not arrival time.** Even at 250 ms, comparisons at 5 s granularity are off by a few hundred ms of traffic.
4. **Ignore Kernel-Network event 18 ("TCP copy").** It fires about as often as event 11 (TCP receive) and would double-count received data. Count only events 10/11/26/27 (TCP send/receive) and 42/43/58/59 (UDP).
5. **Ports in events are big-endian.** `dport 47873` is `0xBB01`, i.e. 443.
6. **Use `ProcessSequenceNumber` for process identity.** Kernel-Process start events (ID 1) include it, and it's unique until reboot. That beats (PID, start time). The same event gives `ImageName` (names for short-lived processes), `ParentProcessID`, `SessionID`, elevation and `PackageFullName` (Store apps). *Phase 1 note:* network events carry only the PID, so the sequence number can't tell their processes apart. Re-mapping the PID on each start event is what handles reuse; the number is decoded but unused.
7. **App figures are payload; adapter figures are frames.** During a download, outbound adapter bytes are mostly payload-free TCP ACKs, which ETW never reports (outbound looked like 37% raw, 70% with header estimate). So:
   - per-app numbers = payload from ETW
   - usage and data-plan totals = adapter counters
   - the difference is shown as **"Protocol overhead & other"** (headers, ACKs, ARP, ICMP, non-TCP/UDP)
8. **UDP receive events are oriented by datagram, not connection** (found in Phase 1). For events 43/59, `daddr` is our own address and `saddr` the sender. Treating `daddr` as remote credited RDP-over-UDP traffic to the PC's own IP, and received multicast to the group address instead of the sender. TCP events and UDP sends use `daddr` = remote.
9. **DNS-Client 3008 events** carry `QueryName`, `QueryStatus` and `QueryResults` (e.g. `type: 5 cname;::ffff:1.2.3.4;`). In the runs, 91.8% of external bytes had a hostname.
10. **ETW sessions are machine-wide and can vanish** (found in Phase 1). Starting a session with a name already in use replaces the existing one, even one owned by another copy of win4tress. `logman stop` or other tools can also stop it. The service checks every 10 s and starts a new session; in a test, an outside stop was recovered in 5 s with no lost events. After an outside stop, don't use the old session's control handle: logger IDs are reused, so stopping through it could stop someone else's session. Stopping a session that is already gone fails with `ERROR_WMI_INSTANCE_NOT_FOUND`; treat that as stopped.
11. **DNS-Client logs a combined A+AAAA lookup twice** (found in Phase 1). The AAAA event carries every address, IPv4 included. The A event has status 87 (`ERROR_INVALID_PARAMETER`) and no addresses; ignore it, or half of all lookups look failed. PTR query names end with the root dot (`4.3.2.1.in-addr.arpa.`).

## Event layouts observed

| Provider / ID | Fields |
|---|---|
| Kernel-Network 10, 11 (TCP v4 send/recv) | `PID, size, daddr, saddr, dport, sport, seqnum, connid` (plus `startime, endtime` on send) |
| Kernel-Network 12 (TCP v4 connect) | `PID, size, daddr, saddr, dport, sport, mss, sackopt, tsopt, wsopt, rcvwin, rcvwinscale, sndwinscale, seqnum, connid` |
| Kernel-Network 42, 43 (UDP v4 send/recv) | `PID, size, daddr, saddr, dport, sport, seqnum, connid` |
| Kernel-Process 1 (start) | `ProcessID, ProcessSequenceNumber, CreateTime, ParentProcessID, ParentProcessSequenceNumber, SessionID, Flags, ProcessTokenElevationType, ProcessTokenIsElevated, MandatoryLabel, ImageName, ImageChecksum, TimeDateStamp, PackageFullName, PackageRelativeAppId, SecurityMitigations` |
| DNS-Client 3008 (query completed) | `QueryName, QueryType, QueryOptions, QueryStatus, QueryResults` |
