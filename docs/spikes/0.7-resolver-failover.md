# Spike 0.7: local resolver failover

**Status:** Passed (2026-10-26) on everything this VM can test, both ways of routing DNS to the resolver. **Decision: route with an NRPT rule, not by changing adapters' DNS servers** (findings below). Sleep/resume and a Wi-Fi switch still need a laptop or a VM with Wi-Fi.
**Tools:** `win4tress-dns` (the product's resolver, release build) on `127.0.0.1:53`, driven by an elevated script that saves the original settings first and starts a separate process that restores them after 150 s whatever happens (it found nothing to do).
**Machine:** Windows 11 Enterprise VM (the dev PC). Ethernet's IPv4 DNS is set by hand to 1.1.1.1 (DHCP offers 1.1.1.1 and 192.168.1.1); Tailscale adds two NRPT rules for its own names; Hyper-V's Internet Connection Sharing holds `0.0.0.0:53`.

## Results against pass criteria

|---|---|---|---|
| Lookups go through the resolver | Within **160 ms** of the change. Through Windows' resolver (`Resolve-DnsName`, as apps ask): a local record answered, example.com and www.microsoft.com (a CNAME chain) resolved, a name on OISD Big came back `0.0.0.0` | Within **75 ms** | ✅ |

The first run's lookups all failed: the test script wrote a config with a broken address (a PowerShell one-element array gotcha), so the resolver kept its empty default and had no upstream. The resolver now reports a config it couldn't load in its status, once, instead of retrying every second.

## Findings

1. **NRPT is the better switch.** Both are as fast, but an NRPT rule for `.` leaves every adapter's own DNS settings alone, which matters more than speed:
   - The upstream servers stay visible and current: what DHCP gives on a new Wi-Fi network, a VPN's servers, a new adapter. With the adapter way, a static `127.0.0.1` hides what DHCP offers (it's still in the registry as `DhcpNameServer` for IPv4, but IPv6 servers from router advertisements aren't), and every adapter that appears needs switching and its original saving.
   - Restoring is deleting one rule, not putting back each adapter's static or DHCP setting.
   - More specific NRPT rules still win: Tailscale's `.ts.net` and reverse zones kept going to 100.100.100.100 (its PTR lookup answered `magicdns.localhost-tailscale-daemon`). VPNs that route their domains with NRPT keep working.
2. **The watchdog timing holds with room to spare.** Four checks 500 ms apart decide in ~1.6 s; Windows picks up either change and a flushed cache in under 100 ms.
3. **Port 53 isn't really in conflict with Hyper-V.** ICS's DNS proxy binds `0.0.0.0:53`; the resolver binds `127.0.0.1:53` and `[::1]:53` beside it and gets loopback traffic. A real conflict (something on `127.0.0.1:53` itself) is detected and reported.
4. **Still to check in the product:** that the service writing the NRPT rule straight to the registry (`…\Dnscache\Parameters\DnsPolicyConfig`) takes effect as fast as the cmdlet, which also notifies the DNS Client.
