# Spike 0.3: Named IP lists (dynamic keyword addresses) without Defender

**Status:** Partly passed (2026-10-25). With Defender Network Protection off, keyword addresses work: blocking follows an update within 0.2 s. But the Windows Firewall COM API can't see a rule's keyword reference, and the third-party-antivirus case is untested. **Decision: keep inline address lists** (the SPEC §7.3 baseline) for v1.
**Tool:** the `NetSecurity` PowerShell cmdlets (`New-`/`Update-NetFirewallDynamicKeywordAddress`, `New-NetFirewallRule -RemoteDynamicKeywordAddresses`) plus a COM read-back, in one elevated script
**Machine:** Windows 11 Enterprise VM (the dev PC), Microsoft Defender Antivirus on, Network Protection off (`EnableNetworkProtection` = 0)

The rule blocked only a private copy of `curl.exe`, which connected to `https://1.1.1.1/` and `https://8.8.8.8/` by IP. The rule, the keyword and the copy were removed at the end; none were left.

## Results against pass criteria

| Criterion (PLAN.md) | Result | Status |
|---|---|---|
| With automatic resolution off, they work when Defender Network Protection is off | Keyword created (`AutoResolve` False, persistent store) in 42 ms. An outbound block rule on the keyword blocked 1.1.1.1 and not 8.8.8.8. After updating the keyword to 8.8.8.8 (16 ms), the block followed **within 161 ms**: 1.1.1.1 reachable, 8.8.8.8 blocked | ✅ |
| …or when Defender is replaced by a third-party antivirus | Not testable here | ⏳ needs the test VM |

## Findings

1. **Updates are cheap.** Changing the keyword's addresses took 16 ms for one address and 33 ms for 1,000, without touching the rule.
2. **COM can't see the keyword reference.** `INetFwPolicy2` lists the rule with its program, but `RemoteAddresses` reads `*`. A COM-only backend can neither create such a rule nor verify it. Our reconciler would see "any address", report a difference, and overwrite the rule.
3. **Using keywords means a second API.** Creating and reading keyword references needs the `NetSecurity` WMI classes (`MSFT_NetFirewallRule`, `MSFT_NetFirewallDynamicKeywordAddress`). The enforcement backend would have to use both WMI and COM, and reconciliation would need both.
4. **Inline lists are fast enough.** Spike 0.2 measured a rule with 1,000 remote addresses at 11 ms and 10,000 at 104 ms. A keyword update is faster, but not in a way users would notice.

## Decision

Inline address lists stay the design (SPEC §7.3). Keywords are reconsidered only if per-host rule churn becomes a measured problem (PLAN risks: "Windows Firewall rule changes too slow under IP churn"), and then together with the WMI backend work.
